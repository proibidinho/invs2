Analise com extrema profundidade os 3 projetos anexos (AWS, Azure e GCP).

IMPORTANTE:
- Não faça uma revisão superficial.
- Não assuma que algo funciona apenas porque existe no código.
- Considere que estes playbooks irão criar centenas de objetos no Jira Assets (CMDB) de uma só vez.
- Qualquer erro pode resultar em centenas de registros incorretos e exigir limpeza manual posterior.
- Portanto quero uma análise preventiva e extremamente criteriosa.

OBJETIVO PRINCIPAL

Validar que os playbooks FULL abaixo possuem exatamente o mesmo comportamento funcional dos respectivos playbooks SINGLE que já foram testados e estão funcionando:

AWS:
- playbooks/sync_single_aws.yml
- playbooks/sync_aws_cmdb.yml

Azure:
- playbooks/sync_single_azure.yml
- playbooks/sync_azure_cmdb.yml

GCP:
- playbooks/sync_single_gcp.yml
- playbooks/sync_gcp_cmdb.yml

O QUE ESPERO DA ANÁLISE

Para cada cloud (AWS, Azure e GCP):

1. Compare detalhadamente o fluxo do SINGLE com o FULL.

2. Identifique qualquer diferença que possa causar:
   - falha de execução
   - criação incorreta de objetos
   - ausência de atributos
   - perda de informações
   - objetos criados com payload diferente
   - comportamento divergente do SINGLE

3. Verifique se TODOS os arquivos de variáveis necessários estão sendo carregados.

Exemplos:
- mapeamento_*_cmdb.yml
- modelo_servidor_map_*.yml
- owner_ids
- aws_vm_specs
- azure_vm_specs
- gcp_machine_specs
- cpu_platform_map
- qualquer outra variável usada pelos filtros Python ou pelas tasks

4. Verifique se todas as variáveis carregadas realmente chegam até os filtros Python.

Exemplo:
- batch_transform_aws_hosts(...)
- batch_transform_azure_hosts(...)
- batch_transform_gcp_hosts(...)

Confirme que os parâmetros passados pelo FULL são exatamente os mesmos utilizados pelo SINGLE.

5. Verifique se o FULL está utilizando os mesmos filtros Python que o SINGLE utiliza.

6. Verifique se o FULL está gerando exatamente o mesmo cloud_data que seria gerado pelo SINGLE.

7. Verifique se o FULL está gerando exatamente o mesmo payload Jira Assets que seria gerado pelo SINGLE.

8. Verifique se algum include_vars existente no SINGLE está faltando no FULL.

9. Verifique se alguma variável necessária está sendo carregada apenas indiretamente e pode resultar em comportamento diferente.

10. Verifique se existe qualquer risco de:
    - variável undefined
    - lista vazia inesperada
    - dicionário vazio inesperado
    - KeyError
    - atributo ausente
    - campo obrigatório não preenchido
    - falha de lookup
    - referência a objectKey inexistente
    - objectAttributeId incorreto
    - erro de sintaxe Ansible
    - erro de escopo de variável

11. Analise os filtros Python e confirme que:
    - todos os atributos necessários são populados
    - modelo_servidor_map é realmente utilizado
    - owner_ids é realmente utilizado
    - *_vm_specs ou gcp_machine_specs são realmente utilizados
    - cpu_platform_map é realmente utilizado no GCP
    - não existem caminhos de execução onde esses dados sejam perdidos

12. Verifique o fluxo completo:

AAP Inventory
→ coleta hosts
→ coleta variable_data (quando aplicável)
→ transformação batch
→ cloud_data
→ geração de payload
→ create.yml
→ Jira Assets

13. Identifique qualquer divergência entre AWS, Azure ou GCP que sugira erro de implementação ou falta de padronização.

14. Se encontrar problemas:
    - explique exatamente o problema
    - mostre o arquivo afetado
    - mostre o trecho afetado
    - explique o impacto real
    - classifique a criticidade:
      - CRÍTICO
      - ALTO
      - MÉDIO
      - BAIXO
